## ローコードツールとしての利用方法

taskall-v2は、remainz系のエンジンを使い、DBモデル構造を生かしたローコードツールです。  
モデル構造については[このリンクの資料](../design/2000002_model_design.md)を、ご一読ください。  
以降の記述では、本ツールの具体的な利用方法について記述します。

---

### 開発環境構築

当該ツールはノーコードツールではないため、必要な画面部品や業務ロジックは自力で実装することを前提としています。  
開発が必要となりますので、まずは開発環境構築をお願いします。

- WindowsもしくはLinuxでの開発が可能です。
- 開発言語はJava(SpringBoot＋thymeleaf)を用いています。
- DBはSQLiteを利用します。
- Widnowsの場合は[WSL環境の構築](../knowledge/wslEnv.md)を行い、Linux(WSL)環境上で開発することを推奨します。
    - ただしGitHubリポジトリを単にローカルにクローンするだけでも動かすことは可能です。
    - Gradleプロジェクトとなっているため、eclipseやVSCode、IntelliJなどで開発可能です。
- [GitHubリポジトリ](https://github.com/freedomRemains/taskall-v2)から資材を取得してください。
- 後はGradleプロジェクトとして認識させれば、eclipseやVSCodeで起動し、利用することができます。

---

### 開発環境上での動作確認

ローカルで当該ツールを起動後、[このURL (http://localhost:8080/taskall-v2/service/top.html) ](http://localhost:8080/taskall-v2/service/top.html)にアクセスすると、動作確認できます。
エラーが起きる場合は、コンソールのエラー表示を確認してデバッグしてみてください。(うまく動かなかったらすいません。。。)

- 「src/main/resources/db/sql」配下にDB初期テーブル及び初期データを持っており、初回起動時に自動でDB構築を行います。
  そのため単に起動しても、すぐに動かせるはずです。
- DBには次の初期権限で、初期アカウントが用意されています。

| ユーザ名                | パスワード | 権限                       | 説明                                             |
| ----------------------- | ---------- | -------------------------- | ------------------------------------------------ |
| guest@account.com       | password   | ゲスト                     | 初回アクセス時は一律でゲストアカウントです。     |
| gnruser@account.com     | password   | 個人ユーザ                 | BtoC向けの個人ユーザ権限のアカウントです。       |
| cmpnyuser@account.com   | password   | 法人ユーザ                 | BtoB向けの法人ユーザ権限のアカウントです。       |
| master@account.com      | password   | 管理者(マスタ)             | システム管理・運用のための管理者アカウントです。 |
| grandmaster@account.com | password   | 特権管理者(グランドマスタ) | あらゆる操作が可能な特権管理者アカウントです。   |

- ユーザ名(メールアドレス)やパスワードは適宜変更してください。
- トップページで「マイページ」のリンクをクリックすると、ログイン情報入力画面となります。
- ここでゲスト以外のアカウント情報を入力することで、そのユーザによるログインが可能です。

### DBメンテナンス

本ツールを理解する上では、最初に管理者もしくは特権管理者でログインし、DBメンテナンス画面を見てみるとよいでしょう。  
[トップ画面](http://localhost:8080/taskall-v2/service/top.html)で「マイページ」のリンクをクリックすると、特権管理者のユーザ名とパスワードがデフォルトで入っています。
そのまま「サインイン」ボタンをクリックするとログインが可能で、「DBメンテナンス」を選択すると、当該ツールに必要な初期DB定義やDBデータを参照できます。

| ボタン     | 説明                                                                     |
| ---------- | ------------------------------------------------------------------------ |
| 定義参照   | 各テーブルのDB定義を参照できます。                                       |
| データ編集 | 各テーブルのデータ編集画面に遷移します。                                 |
| DB構成更新 | custom-[環境名].yamlで設定している位置にあるSQLでDBを更新します。        |
| DB構成取得 | 現在のDBのデータをcustom-[環境名].yamlで設定している出力先に出力します。 |

- 一度「DB構成取得」でDBデータをバックアップしておくことをおすすめします。
- custom-[環境名].yamlの位置にSQLを配置して「DB構成更新」でデータが変わることも、一度確認しておくとよいでしょう。
- 基本的にDBメンテナンスでデータを変更したら「DB構成取得」でバックアップしておくことをおすすめします。
- ある時点の状態にDBを戻したくなったら、バックアップしておいたSQLをcustom-[環境名].yamlの設定位置に配置して「DB構成更新」を実行すると復元できます。
- [モデル構造](../design/2000002_model_design.md)の資料にある通り、DBデータでツールの挙動が変わりますので、バックアップは重要です。
    - 権限の考え方もモデル構造の資料にあります。
    - 以降の拡張でも重要になりますので、ご一読ください。

### 拡張のポリシー

ツールの拡張ポリシーは、次の通りです。

- 最初から存在する部品・業務ロジックを組み合わせて実現できる機能は、ノーコードで作ることができるようにします。
    - ただしデフォルトでできることは少なく、実質的には実装必須となります。
    - 本ツールが将来的に多様な共通部品・業務ロジックを持つようになった場合に、ノーコード運用が可能となる余地を残します。
- いかなる複雑な業務ロジックも入れ込める仕組みとし、複雑な機能の実現可能性を高くします。
    - 業務ロジックはどうしても複雑なものが多くなるため、ノーコードにこだわり過ぎると実現できる機能は少なくなります。
    - そのためツール自体はローコードとし、複雑な拡張にも耐えられるようにします。
- 実装追加に当たっては別途[実装設計資料](../design/2000003_implementation_design.md)もご参照ください。
    - Mockitoを使ったテスト駆動実装により品質を担保する、といった方針が記載されています。
    - issue作成 → フィーチャーブランチ作成 → プルリクという機能拡張時(実装時)の開発フローについても記載されています。

### ケースごとの拡張手順

以降では想定される、よくあるケースごとの拡張手順を記述します。

---

#### アカウントを変更する場合

[トップ画面](http://localhost:8080/taskall-v2/service/top.html)で「マイページ」のリンクをクリックすると、特権管理者のユーザ名とパスワードがデフォルトで入っています。
そのまま「サインイン」ボタンをクリックするとログインが可能で、開発には便利ですが、セキュリティ面では問題があります。

- まずは「アカウント(ACCNT)」テーブルでアカウント情報を編集することを、おすすめします。
- 「src/main/resources/templates/parts/common/20030_commonLogin.html」を編集し、デフォルトで特権管理者ログインできてしまう仕組みもカットすることをおすすめします。
- アカウントに付与する権限の構成を変更する場合は、次の項もご参照ください。

---

#### 権限構成を変更する場合

デフォルトでは、次のような権限が設定されています。

| 権限                       | 説明                                             |
| -------------------------- | ------------------------------------------------ |
| ゲスト                     | 初回アクセス時は一律でゲストアカウントです。     |
| 個人ユーザ                 | BtoC向けの個人ユーザ権限のアカウントです。       |
| 法人ユーザ                 | BtoB向けの法人ユーザ権限のアカウントです。       |
| 管理者(マスタ)             | システム管理・運用のための管理者アカウントです。 |
| 特権管理者(グランドマスタ) | あらゆる操作が可能な特権管理者アカウントです。   |

[モデル構造](../design/2000002_model_design.md)の資料にも記載されていますが、この権限構成は自由に変更可能です。

- 「ロール(APROLE)」テーブルのデータを編集し、権限構成を定義。
- 「アカウント内ロール(APROLE_IN_ACCNT)」テーブルのデータを編集し、アカウントに付与する権限を設定。
- 「要求ロール(REQUIRE_APROLE)」テーブルのデータを編集し、権限ごとに参照できる画面を設定。
- 「ロール内HTMLパーツ(HTML_PARTS_IN_APROLE)」テーブルのデータを編集し、HTMLパーツごとの権限を設定。

---

#### 業務ロジックを追加する場合

たとえば既にある業務ロジック群に、新しいチェックを追加する場合、その業務ロジックのクラスを改修することがまず考えられます。

- SpringBootを採用していますので、業務ロジックは「@Service」アノテーション付きの「～Service」というクラスに実装しています。
- 変更したい業務ロジックのクラスに処理を追加することで、挙動を変えることができます。

ただし変更する業務クラスが複数の画面操作で共通的に呼び出されるような処理である場合、個別の処理追加を共通クラスに入れ込むのは不適切です。
そのような場合は、次のような対応が考えられます。

- 新規に「@Service」アノテーション付きの「～Service」クラスを作成し、個別処理を記述します。
- 「SCR_ELM」テーブルのデータを編集し、追加した新しい業務ロジッククラスを呼び出すようにします。

---

#### 新規ページを追加する場合

アプリに新しいページを追加したい場合は、次のように対応します。  
ページ追加はほぼ実装変更必須のため、[実装設計資料](../design/2000003_implementation_design.md)にあるissue作成 → フィーチャーブランチ作成 → プルリクという開発フローが必要となります。
[README.md](../../README.md)及びそこからリンクでたどれる各資料についても、一度目を通すことをおすすめします。

- 新しいページの外観を決めてください。
    - 既存サイトのページを使う場合は、そのサイトのHTML及びCSS、JavaScriptをコピーします。
    - 近年は生成AIに「こういう感じのページを作って」とお願いし、微調整を行ってページを作ることも多いです。
    - いずれにせよ、表示したいページの外観(HTML、CSS、JavaScript)を何らかの形で用意してください。
- 用意した新しいページのHTMLを元に、「HTMLパーツ(HTML_PARTS)」テーブルに登録するレコードを決めます。
    - 最上位のdivの単位など、おおまかな構成単位でHTMLパーツを分割すると再利用性が高くなります。
    - まずは外観全体を分割せずに1つのHTMLパーツとし、画面表示や動的なデータ表示がうまくいったら分割してもよいです。
- HTMLパーツの構成が決まったら、「src/main/resources/templates/parts」直下にHTMLパーツを追加します。
    - 「1」で始まるパーツで権限を検証し、問題なければ「2」で始まるパーツ本体をfragmentで読み込む構成となっています。
    - 部品の外観だけ再利用し、異なる権限のパーツを作れるよう「1」系と「2」系のHTMLは別にしています。
    - HTMLパーツに対応するHTMLをthymeleafのテンプレートとして用意してください。
- DBの次のテーブルに、レコードを追加します。
    - 「URI_PATTERN(URIパターン)」に、新規ページのURIパターンのレコードを追加します。
    - 「HTMLページ(HTML_PAGE)」に、新規ページをレコードとして追加します。
    - 「HTMLパーツ(HTML_PARTS)」に、新規ページで使用するHTMLパーツのレコードを追加します。
    - 「ページ内パーツ(PARTS_IN_PAGE)」に、HTMLページとHTMLパーツの組み合わせのレコードを追加します。
    - 「スクリプト(SCR)」に、新規ページで使うスクリプトのレコードを追加します。
    - 「スクリプトエレメント(SCR_ELM)」に、スクリプト内で呼び出す各業務ロジックのレコードを追加します。
    - 「要求ロール(REQUIRE_APROLE)」に、新規ページのアクセス権限のレコードを追加します。
    - 「ロール内HTMLパーツ(HTML_PARTS_IN_APROLE)」に、新規ページで使うHTMLパーツの権限のレコードを追加します。
- 本ツールを起動し、無事画面表示できれば新規ページ追加は成功しています。
- 後はHTMLパーツ内の可変要素部分が、業務ロジックで設定した値に置き換わるかなど、細かい動作検証を実施します。
