## モデル構造について

- remainzは、DBモデル構造を生かしたローコードツールです。
    - 既にServlet + JSPの構成で、動くアプリを作っています。
    - URLは「https://github.com/freedomRemains/remainz」です。「develop」ブランチを参照してください。
- 当該ページの記述では各DBテーブルのフィールド物理名を記載しますが、「VERSION」他、どのテーブルにも付与する基本的なフィールドは記載しません。
- また概略をつかみやすいよう、一部テーブルは細かいフィールドの記載を一部省略します。

### URIパターンについて

- URLを指定してWebアプリにアクセスする箇所を起点として、アプリの動作を定義します。  
  DBにURIパターンテーブルを設け、アプリの入口となるURIを管理します。

| テーブル物理名       | テーブル論理名       |
| -------------------- | -------------------- |
| URI_PATTERN          | URIパターン          |

| フィールド物理名     | 型                   | フィールド論理名     |
| -------------------- | -------------------- | -------------------- |
| URI_PATTERN_ID       | INT                  | URIパターンID        |
| URI_PATTERN_NAME     | VARCHAR(256)         | URIパターン名        |
| URI_PATTERN          | VARCHAR(256)         | URIパターン          |

【レコード例】

| URIパターンID        | URIパターン名        | URIパターン                  |
| -------------------- | -------------------- | ---------------------------- |
| 1000001              | TOPページ            | /remainz/service/top.html    |
| 1000101              | エラーページ         | /remainz/service/error.html  |
| 1000201              | マイページ           | /remainz/service/myPage.html |

### URIパターンに対応するHTMページについて

- DBにHTMLページテーブルを設け、URIパターンに対応するHTMLページを管理します。
    - URIパターンごとに GET / POST / PUT / DELETE の挙動を定義できるようにします。
    - GET / POST / PUT / DELETE それぞれの場合に呼び出すスクリプトのIDをテーブルに持たせます。
    - スクリプトとは、任意の業務ロジックを複数組み合わせて呼び出す仕組みです。  
      スクリプトのDB構成については、後述します。

| テーブル物理名       | テーブル論理名       |
| -------------------- | -------------------- |
| HTML_PAGE            | HTMLページ           |

| フィールド物理名              | 型                   | フィールド論理名     |
| ----------------------------- | -------------------- | -------------------- |
| HTML_PAGE_ID                  | INT                  | HTMLページID         |
| PAGE_NAME                     | VARCHAR(256)         | ページ名             |
| URI_PATTERN_ID                | INT                  | URIパターンID        |
| SCR_ID_GET                    | INT                  | GETスクリプトID      |
| RESP_KIND_GET                 | INT                  | 応答種別(GET)        |
| DESTINATION_GET               | INT                  | 遷移先(GET)          |
| SCR_ID_POST                   | INT                  | POSTスクリプトID     |
| RESP_KIND_POST                | INT                  | 応答種別(POST)       |
| DESTINATION_POST              | INT                  | 遷移先(POST)         |
| SCR_ID_PUT                    | INT                  | PUTスクリプトID      |
| RESP_KIND_PUT                 | INT                  | 応答種別(PUT)        |
| DESTINATION_PUT               | INT                  | 遷移先(PUT)          |
| SCR_ID_DELETE                 | INT                  | DELETEスクリプトID   |
| RESP_KIND_DELETE              | INT                  | 応答種別(DELETE)     |
| DESTINATION_DELETE            | INT                  | 遷移先(DELETE)       |

【レコード例】

| HTMLページID         | ページ名             | URIパターンID        | GETスクリプトID | 応答種別(GET) | 遷移先(GET)   | ... |
| -------------------- | -------------------- | -------------------- | --------------- | ------------- | ------------- | --- |
| 1000001              | TOPページ            | 1000001              | 1100001         | forward       | contents.html | ... |
| 1000101              | エラーページ         | 1000101              | 1100101         | forward       | contents.html | ... |
| 1000201              | マイページ           | 1000201              | 1100201         | forward       | contents.html | ... |

- GET / POST / PUT / DELETEそれぞれについて、スクリプトID、応答種別、遷移先を指定できます。
- なおPOST時には原則としてPRGパターンで次のページに遷移させます。次のように記述します。
    - スクリプトID「1100551」で示される業務ロジックを実行後、「updateDbComplete.html」にリダイレクトするという意味になります。

| ... | POSTスクリプトID | 応答種別(POST) | 遷移先(POST)          | ... |
| --- | ---------------- | -------------- | --------------------- | --- |
| ... | 1100551          | redirect       | updateDbComplete.html | ... |

### スクリプトについて

- DBにスクリプトテーブルを設け、複数の業務ロジックを束ねてスクリプト形式で呼び出せるようにします。

| テーブル物理名       | テーブル論理名       |
| -------------------- | -------------------- |
| SCR                  | スクリプト           |

| フィールド物理名     | 型                   | フィールド論理名     |
| -------------------- | -------------------- | -------------------- |
| SCR_ID               | INT                  | スクリプトID         |
| SCR_NAME             | VARCHAR(256)         | スクリプト名         |

【レコード例】

| スクリプトID         | スクリプト名         |
| -------------------- | -------------------- |
| 1100001              | TOP                  |
| 1100101              | エラー               |
| 1100201              | マイページ           |

- スクリプトエレメントテーブルを設け、スクリプトを構成する要素を定義します。
    - レコード例を見ると分かりますが、サービス名が呼び出す業務ロジックとなっています。
    - グループ内順序に従い、順番にサービスを呼び出します。
    - なおサービスの入出力はJSONとします。
    - あるサービスの出力は、スクリプト上、次に呼び出すサービスの入力となります。
    - このようにして複数の業務ロジック間で必要なパラメータを渡していきます。
    - またスクリプトで最後に呼び出したサービスの出力パラメータは、画面に返却されます。
    - この出力パラメータに画面表示用データを含めておくことで、画面表示を更新することができます。(詳細は後述します)

| テーブル物理名       | テーブル論理名       |
| -------------------- | -------------------- |
| SCR_ELM              | スクリプトエレメント |

| フィールド物理名     | 型                   | フィールド論理名       |
| -------------------- | -------------------- | ---------------------- |
| SCR_ELM_ID           | INT                  | スクリプトエレメントID |
| SERVICE_NAME         | VARCHAR(256)         | サービス名             |
| SCR_ID               | INT                  | スクリプトID           |
| ORD_IN_GRP           | INT                  | グループ内順序         |

【レコード例】

| スクリプトエレメントID | サービス名                                    | スクリプトID | グループ内順序 |
| ---------------------- | --------------------------------------------- | ------------ | -------------- |
| 1100001                | com.remainz.web.service.web.GetAccountService | 1100001      | 1              |
| 1100002                | com.remainz.web.service.web.CreateHtmlService | 1100001      | 2              |

- 以上のような仕組みで、URIパターンに対応する業務ロジックを実行します。  
  以降は業務ロジック実行後、画面表示を行うための仕組みについて説明します。

### HTMLパーツについて

- DBにHTMLパーツテーブルを設け、HTMLページを構成するパーツを管理します。

| テーブル物理名       | テーブル論理名       |
| -------------------- | -------------------- |
| HTML_PARTS           | HTMLパーツ           |

| フィールド物理名     | 型                   | フィールド論理名     |
| -------------------- | -------------------- | -------------------- |
| HTML_PARTS_ID        | INT                  | HTMLパーツID         |
| PARTS_NAME           | VARCHAR(256)         | パーツ名             |

【レコード例】

| HTMLパーツID         | パーツ名               |
| -------------------- | ---------------------- |
| 1000001              | システム名表示領域     |
| 1000002              | 共通ヘッダ領域         |
| 1000101              | システムエラー表示領域 |

- HTMLパーツを複数画面で共有できるよう、HTMLページとHTMLパーツの組み合わせテーブルを設けます。
    - URIパターンに紐づく業務ロジックを呼び出すと、紐づくHTMLページを表示します。
    - HTMLページでは、紐づくHTMLパーツを画面に表示します。
    - ページ内パーツのグループ内順序に従って、HTMLパーツはHTMLページ内に配置されます。
    - 出力パラメータにページ内パーツIDをキーとする表示用データをJSONとして投入しておくことで、画面表示を行うことができます。

| テーブル物理名       | テーブル論理名       |
| -------------------- | -------------------- |
| PARTS_IN_PAGE        | ページ内パーツ       |

| フィールド物理名     | 型                   | フィールド論理名     |
| -------------------- | -------------------- | -------------------- |
| PARTS_IN_PAGE_ID     | INT                  | ページ名内パーツID   |
| HTML_PAGE_ID         | INT                  | HTMLページID         |
| HTML_PARTS_ID        | INT                  | HTMLパーツID         |
| ORD_IN_GRP           | INT                  | グループ内順序       |

【レコード例】

| ページ名内パーツID   | HTMLページID         | HTMLパーツID        | グループ内順序 |
| -------------------- | -------------------- | ------------------- | -------------- |
| 1000001              | 1000001(TOPページ)   | 1000001(システム名) | 1              |
| 1000002              | 1000001(TOPページ)   | 1000002(共通ヘッダ) | 2              |

### アカウントについて

- サイトを訪れたユーザを、アカウントとして管理します。
    - サイトを訪れたユーザは、必ずアカウントを持つものとします。
    - 最初にサイトを訪れたユーザは、一律でゲストアカウントと扱います。
    - 後述するロール(権限)は、アカウントに対して付与するものとします。
- DBにアカウントテーブルを設け、アカウントを管理します。

| テーブル物理名       | テーブル論理名       |

| MAIL_ADDRESS         | VARCHAR(256)         | メールアドレス       |
| PASSWORD             | VARCHAR(256)         | パスワード           |

### アカウントとロールの紐づけ

- DBにアカウント内ロールテーブルを設け、各アカウント(ユーザ)が持つロール(権限)を管理します。
    - アカウントIDとロールIDの組み合わせテーブルです。
    - アカウントが持つロールを、このテーブルで管理します。
    - 1つのアカウントには、複数のロールを付与してもよいものとします。
    - 例えば「人事部管理者」「総務部管理者」の両方のロールを持つアカウントも可とします。
    - 次の例は個人ユーザ、法人ユーザ、管理者にロールを分けていますが、ロール設定は任意です。

| ACCNT_ID             | INT                  | アカウントID         |

### 画面表示とロール

- アカウントが持つロールによって画面表示権限を制御できるようにします。
- DBに要求ロールテーブルを設け、HTMLページとロールの組み合わせを管理します。

| テーブル物理名       | テーブル論理名       |
| -------------------- | -------------------- |
| REQUIRE_APROLE       | 要求ロール           |

| フィールド物理名     | 型                   | フィールド論理名     |
| -------------------- | -------------------- | -------------------- |
| REQUIRE_APROLE_ID    | INT                  | 要求ロールID         |
| HTML_PAGE_ID         | INT                  | HTMLページID         |
| APROLE_ID            | INT                  | ロールID             |

【レコード例】

| 要求ロールID         | HTMLページID              | ロールID                |
| -------------------- | ------------------------- | ----------------------- |
| 1000001              | 1000301(DBメンテナンス)   | 1000301(管理者(マスタ)) |
| 1000101              | 1000401(テーブル定義参照) | 1000301(管理者(マスタ)) |

- URL直接指定で権限のないページを表示しようとした場合、このDBテーブルの権限チェックでエラーとなります。
    - ロール制約例外(RoleRestrictionException)が発出され、アプリの仕組みで自動的にエラー処理が行われます。
    - エラー処理の仕組みはカスタマイズ可能とします。
    - 攻撃者に情報を与えないよう、デフォルトでは単純にトップページへのリダイレクトとします。
    - ただしユーザに分かりにくい場合は「権限がありません」というエラー表示のページへのリダイレクトにカスタマイズできるようにします。

### ロールに基づく画面部品の表示制御について

- 前述の要求ロールテーブルはURL直接指定の防御でしたが、これとは別にロールに基づく画面表示制御ができるようにします。
- DBにロール内HTMLパーツテーブルを設け、ロールが持つHTMLパーツを管理します。

| テーブル物理名       | テーブル論理名       |
| -------------------- | -------------------- |
| HTML_PARTS_IN_APROLE | ロール内HTMLパーツ   |

| フィールド物理名        | 型                   | フィールド論理名     |
| ----------------------- | -------------------- | -------------------- |
| HTML_PARTS_IN_APROLE_ID | INT                  | ロール内HTMLパーツID |
| APROLE_ID               | INT                  | ロールID             |
| HTML_PARTS_ID           | INT                  | HTMLパーツID         |
| AUTH_KIND               | VARCHAR(256)         | 権限種別             |

【レコード例】

| ロール内HTMLパーツID | ロールID        | HTMLパーツID                      | 権限種別 |
| -------------------- | --------------- | --------------------------------- | -------- |
| 1000001              | 1000001(ゲスト) | 1000001(システム名)               | read     |
| 1000002              | 1000001(ゲスト) | 1000101(システムエラー表示領域)   | read     |
| 1000003              | 1000001(ゲスト) | 1000201(ログイン情報入力領域)     | edit     |
| 1000004              | 1000001(ゲスト) | 1000701(通知表示領域)             | read     |
| 1000005              | 1000001(ゲスト) | 1001101(エラーメッセージ表示領域) | read     |

- アカウントが持つ権限情報に基づき、画面表示制御ができるようにします。
    - AuthUtil.hasEditAuth([HTMLパーツID], authList)
    - AuthUtil.hasReadAuth([HTMLパーツID], authList)
    - 「authList」はバックエンド側で、DBからロール内HTMLパーツのレコードを取得して設定します。
- レコード例は、ゲストアカウントがログイン情報入力領域の編集権限を持っていること、  
  システム名やシステムエラー表示領域などの参照権限を持っていることを示しています。
- ここでいう編集権限(edit)は入力項目に入力ができることを指します。
- 参照権限(read)のみの場合、入力項目自体を非表示／非活性にします。
- いずれも権限確認のコードをはさむことにより、動的に表示制御ができるようにします。

### 属性について

- データを属性検索できるよう、DBに属性グループテーブル及び属性テーブルを設け、属性を管理します。
- 目薬や胃腸薬などの属性をまとめる医薬品、といった属性グループを管理できるようにします。
- DBに属性グループテーブルを設け、複数属性をひとまとまりにするグループ名を管理します。

| テーブル物理名       | テーブル論理名       |
| -------------------- | -------------------- |
| ATTR_GRP             | 属性グループ         |

| フィールド物理名     | 型                   | フィールド論理名     |
| -------------------- | -------------------- | -------------------- |
| ATTR_GRP_ID          | INT                  | 属性グループID       |
| ATTR_GRP_NAME        | VARCHAR(256)         | 属性グループ名       |

【レコード例】

| 属性グループID       | 属性グループ名       |
| -------------------- | -------------------- |
| 1000001              | 医薬品               |
| 1000101              | 特売品               |

- 個々の属性についても、別途テーブルで管理します。
- DBに属性テーブルを設け、1つ1つの属性を管理します。
    - 属性値の項目は文字列型とし、設定内容は任意とします。
    - enumで定義する連番のように使ってもよく、割引率5%以上で検索できるよう数字としても問題ありません。

| テーブル物理名       | テーブル論理名       |
| -------------------- | -------------------- |
| ATTR                 | 属性                 |

| フィールド物理名     | 型                   | フィールド論理名     |
| -------------------- | -------------------- | -------------------- |
| ATTR_ID              | INT                  | 属性ID               |
| ATTR_NAME            | VARCHAR(256)         | 属性名               |
| ATTR_VAL             | VARCHAR(256)         | 属性値               |
| ATTR_GRP_ID          | INT                  | 属性グループID       |
| ORD_IN_GRP           | INT                  | グループ内順序       |

【レコード例】

| 属性ID               | 属性名               | 属性値               | 属性グループID  | グループ内順序 |
| -------------------- | -------------------- | -------------------- | --------------- | -------------- |
| 1000001              | 目薬                 | 1                    | 1000001(医薬品) | 1              |
| 1000002              | 胃腸薬               | 2                    | 1000001(医薬品) | 2              |
| 1000101              | 3%引き               | 3                    | 1000101(特売品) | 1              |
| 1000102              | 5%引き               | 5                    | 1000101(特売品) | 2              |

- 後は属性を付与したいテーブルとの間で、組み合わせテーブルを作成します。
- 例えばECサイトで売っている製品(PRODUCT)の属性を管理したい場合は、製品内属性(ATTR_IN_PRODUCT)といったテーブルを設けて、属性を管理します。
- あるDBレコードが所定の属性を持っているかは、組み合わせテーブルを属性値で検索して見つけます。
- 属性付与対象のテーブルは作成するサイトによって異なるため、本項では属性検索のためのグループ及び属性自体を定義するにとどめます。
