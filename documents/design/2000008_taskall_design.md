## 助か～るシステムの概要

[現行助か～る(taskall)システム](https://www.taskall.co.jp/ankeninfo/index.jsp?pushedTopMenuButton=top)は、IT求人情報サイトとしての側面を持っています。  
企業が持つIT案件に、人材をアサインすることで生み出される価値に着目しているシステムです。  

- 各企業はそれぞれ、自社の案件や人材を保有しています。
- 案件とは「仕事の案件」を意味しており、案件に人材をアサインすると、案件を持っている企業から対価が支払われます。
    - 契約は1か月更新、3か月更新など様々ですが、対価は単金(1か月当たり何万円という指標)で表します。
- 案件を持っている企業は、自社または他社の人材をなるべく早くアサインしたいと考えます。
- 人材を持っている企業は、自社または他社の案件になるべく早くその人材をアサインしたいと考えます。
- 本サイトでは案件、人材の両方の情報を扱います。  
  それによって複数企業がそれぞれ、案件や人材のアサイン促進を図り、そこに価値が生まれるためです。
- また本サイトでは、案件(仕事)を探している個人向けにも案件情報を公開し、応募可能としています。
- ただし昨今の社会情勢の変化により、各企業とも公開できない案件や人材を持つことが多くなりました。
- 新システムではこうしたニーズにも対応します。
    - 案件に公開可否の属性を付与し、公開／非公開を選択可能とします。
    - 人材も同様に、公開可否の属性を付与します。
    - 各企業は、自社が非公開で持っている案件に、他社の公開人材をアサインすることが可能となります。
    - 同様に各企業は、自社が非公開で持っている人材を、他社の公開案件にアサインすることが可能となります。

【ゲストユーザの特徴(インターネット上からサイトに訪れた人は誰でも、次の情報は参照可能)】

| ポイント                           | 説明                                                                       |
| ---------------------------------- | -------------------------------------------------------------------------- |
| 全ての公開案件情報を参照できる     | どういう仕事(案件)があるのか確認し、サイト利用やサインアップを促進する     |
| 全ての公開人材情報を参照できる     | 自分以外にどういう人材がいるのか確認し、サイト利用やサインアップを促進する |
| 全ての公開案件情報に応募できる     | ただし応募時にはサインアップ必須とする(サイト利用促進、個人ユーザ獲得)     |
| 個人ユーザとしてサインアップできる | 他社案件に応募できるようになる                                             |
| 企業ユーザとしてサインアップできる | 自社案件を管理／公開したり、自社人材に他社案件をアサインできるようになる   |

【個人ユーザの特徴】

| ポイント                               | 説明                                                                   |
| -------------------------------------- | ---------------------------------------------------------------------- |
| 各企業の公開案件に応募できる           | 各企業の非公開案件は不可視のため応募不可                               |
| 自分の人材情報を公開できる             | 各企業から直接アサインの依頼を受けることができる                       |
| 自分の技術経歴を登録・変更できる       | 各企業からの直接アサインを受けやすくできる                             |
| マイページで自分向きの案件を確認できる | 技術経歴や希望単金に見合う他社案件を、マイページで一覧確認できる       |
| メール配信の可否を選択できる           | 見合う案件のメールなどを受け取るかどうかの設定を変更できる             |
| 退会して個人ユーザをやめることができる | 従来システムは退会の仕組みなし、参入障壁になるためサイト退会可能とする |

【企業ユーザの特徴】

| ポイント                               | 説明                                                                   |
| -------------------------------------- | ---------------------------------------------------------------------- |
| 他社の公開案件に応募できる             | ただし他社の非公開案件は不可視のため応募不可                           |
| 自社の人材情報を公開できる             | 各企業から直接アサインの依頼を受けることができる                       |
| 自社人材の技術経歴を登録・変更できる   | 各企業からの直接アサインを受けやすくできる                             |
| 応募中の他社案件の状況を管理できる     | 稼働状況確認中、書類選考中、面談待ち、着任といった状況を確認できる     |
| マイページで自分向きの案件を確認できる | 技術経歴や希望単金に見合う他社案件を、マイページで一覧確認できる       |
| メール配信の可否を選択できる           | 他社案件／人材のメールなどを受け取るかどうかの設定を変更できる         |
| 退会して企業ユーザをやめることができる | 従来システムは退会の仕組みなし、参入障壁になるためサイト退会可能とする |

## 画面構成について

現行助か～るシステムに合わせ、次の画面を用意する。

- 案件一覧(公開案件の一覧画面、属性検索機能付き画面)
- 個人ユーザマイページ
    - 引き合い案件一覧(企業から引き合いが来ている案件の一覧)
    - マッチ案件一覧(デフォルトは更新日時が新しい案件の一覧)
    - 技術経歴入力
    - 案件応募
    - 自分自身を公開人材として登録
- 企業ユーザマイページ
    - 自社持ち人材一覧(稼働状況、営業状況管理)
    - 自社持ち案件一覧(なければ表示しない)
    - マッチング一覧(自社／他社案件と自社人材、自社／他社人材と自社案件)
    - 案件登録
    - 人材登録

この他、ITだけに業務を限らず、ありとあらゆる業務にも助か～るシステムを適用できるようにするため、次のパイロットケースを画面としても用意する。

- 理容師(在宅勤務)
- 生命保険の代理店・募集人(在宅勤務)

## 属性検索について

新助か～るシステムでは「2000002_model_design.md」に記載されている属性を多用する。
前述の取り、従来の助か～るシステムの対象を、広くありとあらゆる業態業種に拡大予定のためである。
そのたびにDB構成を変更し、検索調整を行うのは非効率であると考えられるため、「属性検索」を重要視する。
「案件内属性(ATTR_IN_ANKEN)」「人材内属性(ATTR_IN_JINZAI)」のように、案件や人材といったモデルに属性を付与し、属性での検索を可能とする。

- 例えば「案件分類」という属性グループ(ATTR_GRP)、「商流不問」「年齢不問」「外国籍可」という属性(ATTR)を作るとする。
- 属性検索画面では「案件分類」というパネル内に、「商流不問」「年齢不問」「外国籍可」のチェックボックスを配置する。
- 検索ボタンをクリックすると、チェックが入っている属性で「案件内属性(ATTR_IN_ANKEN)」を検索し、ヒットした案件を表示する。

今後、理容師や生保の他にも諸々の業種業態が増えてきたとき、検索の対象条件も様々に変化することが想定される。
対象となるモデルに属性を付与することで、柔軟な検索ができるようにする。

## 実装に当たって

まずは現行助か～るシステムのメインである案件一覧(公開案件の一覧、ゲストでも参照可能)画面を作る。  
[現行助か～るの案件一覧画面](https://www.taskall.co.jp/ankeninfo/s/QjinSearchServlet?pushedTopMenuButton=search&KBN=SEARCH_DIVISION_NOMAL)を参照のこと。

- 画面上方に新着案件(更新日時が新しい10件)をページネーション付きで表示する。
- 一覧下方には全属性グループのパネル(パネル内には各属性グループ内の属性)を表示し、属性検索による絞り込みができるようにする。
- 例えば「在宅勤務」属性グループ内に「フルリモート」「リモート併用」「常駐」という属性があり、「フルリモート」のみにチェックを入れて検索した場合、フルリモートの最新10件のみの表示に切り替わるものとする。
- スマホからの利用を想定し、レスポンシブデザインとする。
- 画面部品は「レコード一覧領域(20070_commonRecordList.html)」を流用可能であるが、これは一覧表部分がレスポンシブデザインとなっていない。(表示列数によっては極端に横長になるため)
    - 「レコード一覧領域(20070_commonRecordList.html)」はそのまま流用せず、新しい画面部品「案件一覧領域」を用意し、既存コードを流用して実装を行う。
    - 案件一覧では表示項目を「勤務地」「言語」「案件名及び作業内容」「単金」「期間」「詳細リンク」で固定する。
    - PC版は横長の一覧表表示とする。「勤務地」は2/12、「言語」は2/12、「案件名及び作業内容」は4/12、「単金」は2/12、「期間」は2/12、クリックすると詳細にジャンプ、の構成とする。
    - スマホ版は、1行目「勤務地(6/12)」「言語(6/12)」、2行目「案件名及び作業内容(12/12)」、3行目「単金(6/12)」「期間(6/12)」、クリックすると詳細にジャンプ、の構成とする。
- 属性検索も同様にレスポンスデザインを意識する。
    - いずれも属性グループでパネルを用意し、その中に各属性を表示する。
    - PC版は1行3属性まで、それぞれ4/12で配置。
    - スマホ版は1行1属性(12/12)で配置する。

## 案件について

案件一覧画面新設に当たり、案件テーブルを次のように規定する。(定型カラムは記載省略)

| テーブル物理名       | テーブル論理名       |
| -------------------- | -------------------- |
| ANKEN                | 案件                 |

| フィールド物理名     | 型                   | フィールド論理名                 |
| -------------------- | -------------------- | -------------------------------- |
| ANKEN_ID             | INT                  | 案件ID                           |
| ACCNT_ID             | INT                  | 案件所有企業ユーザ(外部キー)     |
| ANKEN_NAME           | VARCHAR(256)         | 案件名                           |
| DESCRIPTION          | VARCHAR(8192)        | 説明                             |
| WORK_PLACE           | VARCHAR(256)         | 勤務地                           |
| TERM                 | VARCHAR(256)         | 期間                             |
| AGE                  | VARCHAR(256)         | 年齢(不問、50代までなど)         |
| BILLING_RATE         | VARCHAR(256)         | 単金(スキルに応じる、～60万など) |
| MIN_RATE_NUM         | INT                  | 最低単金(数値化できる場合のみ)   |
| MAX_RATE_NUM         | INT                  | 最高単金(数値化できる場合のみ)   |
| RECRUIT_NUM          | INT                  | 募集人数                         |
| STATUS               | INT                  | ステータス(1：募集中、2：充足終了、3：募集終了) |

- 案件の公開／非公開は「公開属性」を付与して公開／非公開の制御を行うものとする。
- 外国籍可／不可は「外国籍可」の属性が付与されているかどうかで判断する。
- 案件は掲載から2週間で「3：募集終了」とする。(無理や業務や安すぎる単金などで流れる案件)
- ただしそれ以前に人員充足のために終了した場合は「2：充足終了」を記録する。(充足率はまともな案件を出す企業かどうかの指標となる)
- なお「言語」「業種」「工程」「職種」「DB」「フレームワーク」「案件分類」「在宅勤務」などの属性は、バッジとして画面表示する。  
  (案件一覧から飛べる案件詳細画面にて、その案件が持っている属性のバッジを表示するイメージ)

| テーブル物理名       | テーブル論理名       |
| -------------------- | -------------------- |
| ATTR_IN_ANKEN        | 案件内属性           |

| フィールド物理名     | 型                   | フィールド論理名 |
| -------------------- | -------------------- | ---------------- |
| ATTR_IN_ANKEN_ID     | INT                  | 案件内属性ID     |
| ANKEN_ID             | INT                  | 案件ID           |
| ATTR_ID              | INT                  | 属性ID           |

## 現行助か～るの案件一覧画面に見る特徴について

一見しても、案件一覧画面には次のような問題が見られます。

- 「言語」が「Java」で「職種」が「Javaエンジニア」など、「言語」と「職種」に意味重複が多く、表に2列取る意味が薄い。
- アイコン表示欄を見ることがほとんどなく、表の幅だけ取ってしまっている。
- 下方にある検索についても、プラットフォームや業務、職種など、異なる項目グループ間で似たような項目が多数あり、分かりづらい。
- 全般に表示量ばかり多くて見づらく、使うのが面倒な印象を与えやすい。(検索グループも、1グループ7つ程度までが望ましい)
- さらに先の詳細画面でも項目数が多いわりに役に立たない情報が多く、全般に見づらく、並びも分かりづらい。

ソースコードも合わせてみると、度重なる改修によって管理が混乱しているものと判断できます。  
案件一覧や案件詳細は特に重要かつ複雑な画面・機能なので、集中的に「こうすべき」という依頼が出やすく、複数の依頼間の矛盾点なども解決されないまま成果のみを求められた結果、そのときどきで決めた内容や無駄な項目が残っている状態です。  
以降の改修では可能な限り仕様や表示をシンプルに、操作は分かりやすく、を目指しますが、依頼者が直接改修依頼すると「こうしてほしい」のみの要望により上記と同様の状況に陥りやすいです。  
属性をうまく利用してください。毎回DBの案件テーブルに項目を追加したり、制御を変更すると、管理可能性が徐々に低下していきます。
「～属性を持っているか」 → YES → (固有処理を実行)、のようにDBモデルとは別の付加属性に対する操作を累積すると、外したり付け直すことが容易になります。
