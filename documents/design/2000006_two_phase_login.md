二段階認証の実装

現状のログインの仕組みに二段階認証の仕組みを追加する。

本ドキュメントは issue #11 で提案された初版仕様を、2回の仕様レビューで発見された
論理的なバグ・設計上の欠落・セキュリティ上の懸念を踏まえて改訂したものである。
初版との主な差分は次の4点。

- 「ログイン試行の状態」を保持するテーブルと、「アカウント単位の認証失敗回数・ロック」を
  保持するテーブルを分離した(詳細は後述)。初版は1テーブル・1アカウント1行構成のため、
  正規ユーザの複数デバイス・複数ブラウザからの同時ログインと、パスワードを知らない
  第三者による妨害行為とを区別できず、後者によって前者の進行中の認証状態が壊されて
  しまう欠陥があった。
- 「ログイン試行」テーブルのレコードを毎回物理削除して作り直す方式を廃止し、
  既存レコードがあれば**更新**する方式に変更した(初版のままだと認証失敗回数が
  常にリセットされてしまい、5回失敗によるアカウントロックが実質的に機能しないバグが
  あったため)。
- 6桁のパスコードそのものを保存するカラムが初版に存在しなかったため、
  `PASSCODE_HASH`カラムを追加した(平文保存はせず、ハッシュ化して保存する)。
- 「ログイン試行」テーブルの検索キーに`SESSION_ID`を含めることで、他セッションの
  二次認証パスコードを別セッションから使い回す攻撃を、自然に防止できるようにした。

### 二段階認証の処理概略

- メールアドレス及びパスワードによる認証は、次の通り変更する。
    - 認証成功でもまだログインとは扱わない。制御用テーブルに「first_auth_pass(一次認証通過)」というステータスを登録するにとどめる。
    - ユーザが誤ったメールアドレス、パスワードを入力した場合は、エラー表示する点は現状と変わらない。
- メールアドレス及びパスワードによる認証が成功したら、メールアドレス宛に6桁のランダムな数字のメールを送信する。
    - メールタイトルは「二段階認証パスコード」、本文は「次の6桁の数字をご入力ください。(改行)  XXX XXX」とする。  
      (改行後に半角スペース2文字を入れ、3文字、半角スペース、3文字で、6桁の数字を記述する)
    - 画面は6桁の数字の入力モードとなって待機する。
    - メールの有効期限は5分とする。
    - ユーザが正しく数字を入力した場合はログイン成功と見なし、ログイン後の画面(マイページ)に遷移する。
    - ユーザが誤った数字を入力した場合は、エラーメッセージを画面に表示して再入力を待機する。
    - ユーザが5回誤った数字を入力した場合は、アカウントを15分間ロック状態とする。

### 制御用のテーブル追加

二段階認証を制御するため、「ログイン試行(LOGIN_STATUS)」テーブルと
「アカウント認証ロック(ACCNT_AUTH_LOCK)」テーブルを新設する。両者の役割を明確に分離する。

- 「ログイン試行(LOGIN_STATUS)」：**1回のログイン試行(=1ブラウザセッション)の状態**を
  保持する。同一アカウントであっても、セッションが異なれば複数行が同時に存在してよい
  (正規ユーザの複数デバイス・複数ブラウザからの並行ログインを妨げないため)。
- 「アカウント認証ロック(ACCNT_AUTH_LOCK)」：**アカウント単位で1行のみ**、認証失敗回数と
  ロック状態を保持する。どのセッションからの失敗であっても、この1行に対して合算する
  (ブルートフォース対策の集計はセッションをまたいでアカウント全体で行う必要があるため)。

#### ログイン試行(LOGIN_STATUS)

| テーブル物理名       | テーブル論理名       |
| -------------------- | -------------------- |
| LOGIN_STATUS         | ログイン試行         |

| フィールド物理名     | 型                   | フィールド論理名     |
| -------------------- | -------------------- | -------------------- |
| LOGIN_STATUS_ID      | INT                  | ログイン試行ID       |
| ACCNT_ID             | INT                  | アカウントID         |
| SESSION_ID           | VARCHAR(256)         | セッションID         |
| CURRENT_STATUS       | VARCHAR(256)         | 現在ステータス       |
| PASSCODE_HASH        | VARCHAR(256)         | パスコードハッシュ   |
| EXPIRES_AT           | TIMESTAMP            | 有効期限             |
| (VERSION以下は略)    |                      |                      |

※　「EXPIRES_AT」の次のフィールドは「VERSION」、以降、全テーブル共通の定型フィールドとする。

- 「現在ステータス」には、次のいずれかの値が入るものとする(アカウント全体のロック状態は
  このテーブルでは扱わず、「アカウント認証ロック」テーブル側で管理する。詳細は後述)。
    - 「not_auth(未認証)」
    - 「first_auth_pass(一次認証通過)」
    - 「first_auth_fail(一次認証失敗)」
    - 「second_auth_fail(二次認証失敗)」
    - 「auth_success(認証成功)」
- 「PASSCODE_HASH」は、送信した6桁のパスコードを一方向ハッシュ化した値を保存するカラムとする。
  平文の6桁数字はDBに保存しない。二次認証の照合時は、ユーザが入力した6桁数字を同じ方式で
  ハッシュ化し、本カラムの値と比較する。「first_auth_pass」以外のステータスでは値を持たない(NULL)。
- `(ACCNT_ID, SESSION_ID)`の組み合わせに一意制約を付与する(同一セッションからの重複行は
  作らない。別セッションからの行は別レコードとして共存できる)。
- 「TBL_DEF.txt」に「ログイン試行(LOGIN_STATUS)」テーブルの定義を追加する。
    - 「TBL_DEF_ID」は「1002201」始まりの連番とする。
    - カラム定義は上記の通りとする。
    - `ACCNT_ID`行・`SESSION_ID`行の「EXTRA」列に、複数フィールドにまたがる一意制約を表す
      記法として「UNIQUE_1_1」「UNIQUE_1_2」(先頭の数字が制約グループ番号、末尾の数字が
      グループ内の並び順)を記述する。
    - **現状の`CreateTableSqlBuilder`は「EXTRA」列を一切参照していない**(既存データの
      「AUTO_INCREMENT」という値も、実際には主キー自動採番の判定に使われておらず、
      `KEY_DIV=PRI`から別ロジックで決定している死んだ記述である)。そのため本テーブルの
      実装時には、`CreateTableSqlBuilder`に「EXTRA」列のUNIQUE_x_y記法を解釈し、
      グループ番号ごとに`UNIQUE (col1, col2)`句をCREATE TABLE文へ追加するロジックを
      新規に実装する必要がある。
    - なお「DB構成取得」(`LiveTableColumnDefLoader`等)は、稼働中DBの実スキーマを
      イントロスペクションするのではなく、**DB内に保持された`TBL_DEF`テーブル自身の行データ
      をSELECTしているだけ**であるため、「TBL_DEF行データ→CREATE文」という生成ロジックが
      決定的である限り、「取得」「更新」を何度繰り返しても同一のSQLが再生成され、
      DB構成の完全な再現性は損なわれない。

#### アカウント認証ロック(ACCNT_AUTH_LOCK)

| テーブル物理名       | テーブル論理名           |
| -------------------- | ------------------------ |
| ACCNT_AUTH_LOCK       | アカウント認証ロック     |

| フィールド物理名     | 型                   | フィールド論理名         |
| -------------------- | -------------------- | ------------------------- |
| ACCNT_AUTH_LOCK_ID    | INT                  | アカウント認証ロックID   |
| ACCNT_ID              | INT                  | アカウントID             |
| FAIL_CNT              | INT                  | 認証失敗回数             |
| LOCKED_UNTIL          | TIMESTAMP            | ロック解除予定時刻       |
| (VERSION以下は略)     |                      |                            |

※　「LOCKED_UNTIL」の次のフィールドは「VERSION」、以降、全テーブル共通の定型フィールドとする。

- `ACCNT_ID`に一意制約を付与する(1アカウントにつき、このテーブルの行は高々1件)。
- 「LOCKED_UNTIL」がNULL、または現在時刻より過去の場合は「ロックされていない」ものとして扱う。
  現在時刻より未来の場合のみ「ロック中」とする。
- 「TBL_DEF.txt」に「アカウント認証ロック(ACCNT_AUTH_LOCK)」テーブルの定義を追加する。
    - 「TBL_DEF_ID」は「1002301」始まりの連番とする(「ログイン試行」テーブルの採番ブロック
      100件分の次のブロックとする)。
    - カラム定義は上記の通りとする。

### 二段階認証処理

一次認証(メールアドレス・パスワード)のPOST処理は、次の手順で実行する。

1. 入力されたメールアドレスでアカウントテーブルを検索する。
    - メールアドレスがアカウントテーブルにない場合は、以降のテーブル操作は一切行わず、
      現状と同様のエラー表示を行う(アカウント存在有無を推測されないようにするため)。
2. アカウントが見つかった場合、「アカウント認証ロック(ACCNT_AUTH_LOCK)」テーブルをアカウントIDで検索する。
    - 行が存在し、「LOCKED_UNTIL」が現在時刻より未来の場合：「アカウントは現在、
      ロックされています。(改行)しばらくしてから再度アクセスしてください。」というエラーを
      画面に表示し、以降の処理は行わない(このセッションが今回のロックの原因かどうかに
      関わらず、アカウント全体を一律で保護する)。
    - 行が存在しない、または「LOCKED_UNTIL」が現在時刻を過ぎている(=ロック解除済み)場合：
      次の認証処理に進む。
3. 「ログイン試行(LOGIN_STATUS)」テーブルを`(ACCNT_ID, SESSION_ID)`(現在のセッションID)で検索する。
    - 行が存在しない場合、または存在するが「EXPIRES_AT」を過ぎている場合(過ぎている場合は
      物理削除してから)：新規作成する。「現在ステータス」は「not_auth(未認証)」、
      「有効期限」は30分後とする。
    - 行が存在し、期限内の場合：そのまま更新対象として使用する(このセッション専用の行なので、
      他セッションの状態を気にする必要はない)。
4. メールアドレス・パスワードによる認証を実行する。
    - 認証が成功した場合：
        - `LOGIN_STATUS`行を次の内容で更新する。「現在ステータス」は「first_auth_pass(一次認証通過)」、
          「有効期限」は5分後。6桁のランダムな数字を生成し、ハッシュ化して「PASSCODE_HASH」に
          保存した上で、メールアドレス宛に二段階認証メールを送信する。
        - `ACCNT_AUTH_LOCK`行が存在する場合は、「FAIL_CNT」を0にリセットする
          (一次認証を突破したので、ここまでの失敗回数はクリアする)。
    - 認証が失敗した場合：
        - `LOGIN_STATUS`行の「現在ステータス」を「first_auth_fail(一次認証失敗)」に更新する
          (「有効期限」は変更しない)。
        - `ACCNT_AUTH_LOCK`行が存在しなければ新規作成(「FAIL_CNT」=1)、存在すれば
          「FAIL_CNT」を1増やす。「FAIL_CNT」が5に達した場合は「LOCKED_UNTIL」を
          15分後に設定する。

二次認証(6桁の数字入力)のPOST処理は、次の手順で実行する。

1. セッションに保持している(一次認証成功時に記録した)アカウントIDで、
   「アカウント認証ロック(ACCNT_AUTH_LOCK)」テーブルを検索する。
    - 「LOCKED_UNTIL」が現在時刻より未来の場合：未ログインのTOP画面に遷移させ、
      「アカウントは現在、ロックされています。(改行)しばらくしてから再度アクセスしてください。」
      というエラーを画面に表示し、以降の処理は行わない(他セッションの失敗が原因でロックが
      かかった場合も含め、アカウント全体を一律で保護する)。
2. 「ログイン試行(LOGIN_STATUS)」テーブルを`(ACCNT_ID, SESSION_ID)`(現在のセッションID)で検索する。
    - 行が存在しない場合：未ログインのTOP画面に遷移させ、「認証の有効期限が切れました。
      再度、メールアドレス及びパスワードによる認証をお願いします。」というエラーを画面に表示する。
    - 現在時刻が「有効期限」を過ぎている場合：行を物理削除した上で、未ログインのTOP画面に
      遷移させ、上記と同じ有効期限切れのエラーを画面に表示する。
    - 「現在ステータス」が「first_auth_pass(一次認証通過)」でも「second_auth_fail(二次認証失敗)」
      でもない場合：不正な遷移とみなし、上記と同じ有効期限切れのエラーを画面に表示する。
      (「second_auth_fail」は二次認証の再入力待機中の正常な状態であり、「first_auth_pass」と
      同様に再入力を許可する必要がある。誤って「first_auth_pass」のみを許可条件にすると、
      一度でも6桁入力を間違えた直後の再入力ができなくなってしまうため、両方を許可する)
    - ※検索キーに`SESSION_ID`を含めているため、他セッションで発行されたパスコードを
      別セッションから入力しても、そもそも行が見つからず「有効期限切れ」と同じ扱いになる
      (セッション不一致を専用のエラーメッセージで通知しないことで、情報漏洩を防ぐ)。
3. 上記いずれにも該当しない場合、入力された6桁の数字をハッシュ化し、「PASSCODE_HASH」と比較する。
    - 一致した場合：
        - 「現在ステータス」を「auth_success(認証成功)」に更新した上で、SpringBootの
          ログインセッションを確立する(実際のログイン処理)。
        - `LOGIN_STATUS`行を物理削除する(役目を終えた行を残さない)。
        - `ACCNT_AUTH_LOCK`行が存在すれば、あわせて物理削除する(正常にログインできたため、
          それまでの失敗回数の記録は不要)。
        - ログイン後の画面(マイページ)に遷移する。
    - 一致しない場合：
        - `LOGIN_STATUS`行の「現在ステータス」を「second_auth_fail(二次認証失敗)」に更新する
          (「有効期限」は変更しない。一次認証通過時に設定した5分間の中で試行できる回数を
          制限する意図のため)。
        - `ACCNT_AUTH_LOCK`行が存在しなければ新規作成(「FAIL_CNT」=1)、存在すれば
          「FAIL_CNT」を1増やす。「FAIL_CNT」が5に達した場合は「LOCKED_UNTIL」を15分後に設定し、
          未ログインのTOP画面に遷移させ、「アカウントは現在、ロックされています。(改行)
          しばらくしてから再度アクセスしてください。」というエラーを画面に表示する。
          5回未満の場合は、エラーメッセージを画面に表示し、6桁の数字の再入力を待機する。

### 特殊ケースの想定

- メールアドレス・パスワードのログイン画面のままセッションタイムアウト時間(30分)を経過する。そしてログイン(POST)を実行。
    - 初回であり、まだ`LOGIN_STATUS`行が作られていない場合。
        - 初回ログインの場合はレコード作成からの通常処理となる。問題なし。
    - 既にログインしているが、ログイン前に起動していた別タブでセッションタイムアウト後に認証情報を入れてログイン。
        - 錯覚しやすいが、これはそもそもセッションタイムアウトとなる。(SpringBootのログアウト処理が走る)
        - セッションタイムアウトにより新しいセッションIDでの再ログインとなるため、`LOGIN_STATUS`は
          `(ACCNT_ID, SESSION_ID)`が変わり別行として新規作成される。(問題なし)
    - 未ログインだが5回未満のログイン失敗がある。
        - 同一セッションであれば`LOGIN_STATUS`行は有効期限内なら更新方式で引き継がれ、
          `ACCNT_AUTH_LOCK`の失敗回数も維持されたまま再試行できる。(問題なし)
    - 未ログインかつロック状態である。
        - `ACCNT_AUTH_LOCK`の「LOCKED_UNTIL」(15分後)は、セッションタイムアウト(30分)より
          先に到来するため、その時点でロックは自然に解除される。(問題なし)
- 一次認証を通過したまま、5分が経過する。(有効期限切れ)
    - 6桁の番号を入力。
        - `LOGIN_STATUS`行が期限切れのため、二段階認証の冒頭部処理でエラーとなる。問題なし。
    - 事前に起動していた別タブ(別セッション)でメールアドレス・パスワードを入力。
        - 別セッションの`LOGIN_STATUS`行として新規に処理される。元のタブの期限切れ行には
          影響しない。(問題なし)
- 一次認証を通過したまま、セッションタイムアウト時間(30分)を経過する。
    - 6桁の番号を入力。
        - `LOGIN_STATUS`行が期限切れのため、二段階認証の冒頭部処理でエラーとなる。問題なし。
    - 事前に起動していた別タブ(別セッション)でメールアドレス・パスワードを入力。
        - 別セッションの`LOGIN_STATUS`行として新規に処理される。(問題なし)
- 正規ユーザが別PC・別ブラウザから同時にログインを試みる(2つの独立したセッション)。
    - 各セッションはそれぞれ独立した`LOGIN_STATUS`行(異なる`SESSION_ID`)を持つため、
      片方の操作(パスワード再入力や誤入力)がもう片方の二次認証待ち状態を破壊することはない。
      (初版で懸念されていた問題を解消)
    - ただし、どちらかのセッションでの失敗は`ACCNT_AUTH_LOCK`に合算されるため、
      例えば片方のセッションで4回誤入力した状態でもう片方のセッションで1回誤入力すると、
      合算で5回に達しロックされる。この場合は両方のセッションがロックの影響を受ける
      (アカウント全体を保護するための意図的な仕様。次項も参照)。

### 「ログイン試行(LOGIN_STATUS)」の定期クリーンアップ

「ログイン試行」テーブルの行の物理削除は、上記の各POST処理の中で「そのセッションが
再度アクセスしてきた時」にしか実行されない。そのため、次のようにユーザーが途中で
離脱した場合、行が誰にも削除されないまま残り続けてしまう。

- パスワード認証まで行ったが、6桁のパスコードを一度も入力せずブラウザを閉じた場合。
- 6桁のパスコードを誤入力した後、再入力せず離脱した場合。

この問題への対応として、期限切れの行を定期的に削除するスケジュール処理を追加する。
本件は単純な期限切れ行の削除のみであり、SpringBatchほどの仕組みを導入するのは
過剰であるため、Spring標準の`@Scheduled`によるシンプルな定期実行(例: 10分間隔で
「EXPIRES_AT」が現在時刻を過ぎている行を削除する)で対応する。

- 「アカウント認証ロック(ACCNT_AUTH_LOCK)」テーブルは、1アカウントにつき高々1行であり、
  アカウント数に比例して有界であるため、同様の定期クリーンアップは必須ではない
  (行が残っていても実害はなく、`LOCKED_UNTIL`が過去であれば単に「ロックされていない」
  ものとして扱われるだけである)。ただし、実装コストが小さいのであれば、
  「ログイン試行」と合わせて期限切れ行を削除してもよい。

### 残存する既知の懸念事項(要検討)

- テーブル分割により、「パスワードを知らない第三者の1回の誤入力だけで、正規ユーザの
  二次認証待ち状態が即座に破壊される」という問題は解消したが、**第三者が5回連続で
  誤ったパスワードを送信すれば、依然としてアカウント全体が15分間ロックされ、
  進行中の正規ユーザのログインも道連れでブロックされる。** これは一般的なアカウント
  ロック機構に共通する既知のトレードオフであり(ロックによるブルートフォース対策と、
  ロックによるサービス妨害の可能性は表裏一体)、本仕様では許容する前提とする。
    - 追加対策が必要な場合は、IPアドレス単位のレート制限を別途組み合わせる、
